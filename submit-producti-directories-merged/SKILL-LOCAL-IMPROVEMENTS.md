# 外链自动提交合并版 · 本地通用改进（v1.2-local）— SKILL 增补

> 本段为在**外链自动提交合并版（SPD IDP V1）**基础上的**本地通用化改进**（非替换核心规则、复用其审计脚本/记录模板）。
> 目的：让本技能更通用、可裁剪、可大规模批量，并把实战踩过的坑固化为规则。
> 本公开合并版不携带项目私有执行器；文中“复用工具”指当前任务中已核验存在、且满足本技能约束的等价工具，不得臆定私有文件路径可用。

## 0.0 核心定位（用户明确，2026-08-26）
> **SPD IDP 的核心不是"完全自动化"，而是**：**高效批量执行"简单可自动化"的外链推广工作 → 筛选出"需要人工执行的复杂网站" → 人工集中收尾**。既提批量效率，又改善人机交互体验。
- **机器职责**：把简单可自动化的站点（直投表单、常规注册/登录验证、低风险验证等）**整批高效执行**——批量扫描、填表、提交、取证（§2/§9/§16/§18 系列）。
- **筛选职责**：把**复杂站点**（强反自动化、支付、强制互链、需编辑内容/账号归属异常、不可达等）**筛出**并进人工队列（§4/§8.1/§17/§18.1/§19），**批末统一交人工**（§8），机器只保留标签页与字段卡。
- **人机体验**：机器"清道夫式"先扫完全自动范围；人只处理机器筛出的复杂点，按字段卡连续完成，不再被逐站打断。
- 一切规则（自动化程度、验证分级、记录、审计）都服务于"批量高效 + 人工只做复杂点"这个核心。

## 0. 规则优先级与一致性
- 本增补只补充操作细节，不覆盖核心技能、网站条款、平台安全边界或当前批次授权。
- 付费链接、强制互链、伪造资料、批量灌水和违反网站条款的路径一律停止；任何“放宽覆盖”的批次策略都不能改变这些边界。
- “已预填”“已保存草稿”“人工已点击”都不是成功提交；成功必须有原生回执、账户状态、邮箱回执或公开页面等可核验证据。
- 文档中的示例值必须是占位符，不得使用看似真实的口令、邮箱、令牌或绝对路径。
- **本机凭证口径（2026-08-26 用户确认）**：用户确认本机已有防泄露措施，**明文凭据可按本地策略写入（本地）记录**；仅当记录将被外发/跨机器共享时，先隔离敏感信息并在外发前提醒。

### 0.1 教训→检查项 固化机制（2026-08-27 用户要求）
> **读了不算应用，过了 `EXEC-CHECKLIST.md` 并留痕才算**。避免"记录了已读仍复发"。
- **新教训必须增量固化为检查项**（`EXEC-CHECKLIST.md` 增补 A/B/C/D 对应条目，或按站附录），细则才进本文件；只写长文档＝未应用。
- **每站执行前过 A/B 相关项、提交/判定后过 C/D 项**，并把 `checklist PASS/FAIL`（FAIL 写明原因）写入该站记录（§20 交付可见）；未过不得提交。
- **上下文压缩恢复后**：先对当前批过一遍清单再行动（SKILL.md 已同步）。
- 高发项速记：站内去重(§11.1)、值回读/fail-fast(§7.9)、媒体异步解锁(§16.2)、不碰总控客户端(§6.1)、paid 路径不停(§7.8)、曝光识别含 project(§19.1)。

## 1. 通用化（不要机械硬套）
- V1 的队列/去重/验证优先/幂等框架**通用适用**；站点类型分类（direct form / account required / manual verification / email verification / paid/reciprocal / unavailable / ineligible / unknown）直接复用。
- 步骤是**手段按需取用**：直投型→填表；需注册→走注册器；社区/媒体→另走内容流程；付费/互链→默认跳过；CF/空/不可达→unavailable。
- 不做"为显得完整补每站全字段"；状态如实、按真实发生写。

## 2. 批量执行器（写一次、按配置分片）
- 用 CDP 直连指纹浏览器（端口/资料用参数）跑分片；配 `BB_PORT` / `ONLY` / `ROUT`。
- 输入：站点列表(JSON) + 字段配置；输出必须使用正式状态模型：`duplicate — no action` / `submitted` / `submission outcome unknown` / `blocked — manual verification` / `unavailable`，并附证据。去重无法完成但批次授权允许时，记录 `Duplicate check: inconclusive — user-authorized direct attempt` 后进行一次最终提交尝试；旧执行器输出应在写记录前映射：`already_listed` → `duplicate — no action`；`captcha_wait` → `blocked — manual verification`。
- 写脚本避免 heredoc 嵌套 `${}`/反引号坏文件 → 用 write 工具落盘再执行；每站 try/catch 防单点中断整批。
- 可选实现：使用当前任务中已核验的 CDP 客户端和批量执行器；不得假定本技能附带某个固定私有脚本。

## 3. 字段卡一次给全（减少往返）
- 提交前按站点生成/准备好完整字段卡：每个字段=确切值，含**图片文件路径且尺寸/大小已合规**；字段卡可写在当前批次记录或工作区，不依赖本技能未提供的模板。
- 手填站点：一次把整个字段卡给人，人直接照填；不再"贴一个表单回一字段"。

## 4. 人工队列批处理 + token 防过期
- 遇验证码/口令策略/CF → 先按 **§18.1 分级自动尝试**（一级/二级低风险验证），**强反自动化与尝试超限**的项目才归**人工队列**，攒批（建议 3–10 项）一次交人，不整批停。
- **人工接力标签页必须保留**：一旦将项目移入人工队列，保留该站对应的浏览器标签页和当前验证状态；不得像普通只读预检一样自动关闭临时标签页。记录站点、目标 URL、target/tab 标识、阻塞原因和所需人工动作，并明确告知用户该标签页已保留。
- **暂停边界（2026-09-17 更新）**：一旦遇验证，无论验证在流程前、中、后出现，agent 都必须在人工接力前预填所有可如实填写的产品字段、上传适用素材，并按 §18.4 选择无费用的营销订阅；不得点击最终提交。只有缺少已核实值或站点不适用的字段可留空，且须写明原因。不得以“待验证”为由留下空表单或关闭标签页。用户完成登录、邮箱/SMS 验证或其他指定动作后，以“已完成验证／继续”明确交回，agent 先重读页面状态和 token 有效性再继续。
- **验证码例外**：验证码 token 通常极短有效。若该站要求验证码与最终提交连续完成，agent 保留并定位到该标签页，由用户完成验证码后**立即自行点击最终提交**；agent 随后只读核验回执，绝不重提。若验证码与提交可以分离，则遵循上一条，由用户交回后再由 agent 完成获授权的下一步。
- **captcha token 有效期极短**：人"勾选后立即点提交"，agent 不要代点（会因 token 过期被拒）；agent 在人提交后负责核验结果。
- Google/OAuth 类站若已登录 Google，优先用 OAuth 登录以减少验证码；若站点 OAuth 配置损坏则转邮箱注册（验证走 Gmail/飞书，按口径"自动或人工"）。

## 5. 记录与审计一次做对
- 以 `scripts/audit_submission_record.py` 作为记录完整性单一事实来源；修改记录格式时必须同步更新脚本与回归测试。
- **记录生成器**把审计约束（枚举、phase/status 组合、Source list 与 Submission URL 一致、时间线 require、Quality gate 子项、与记录范围相符的敏感信息规则）**内置**，一次产出即 Valid；后续增量为 append，不整批重算。
- 记录口径（2026-08-26 用户口径）：默认用别称（alias-*）与受控证据 ID，并以 `shareable` 范围审计；本机受保护、且用户已确认时，明文凭据可写入标记为 `local-controlled` 的本地记录，必须使用 `audit_submission_record.py --record-scope local-controlled` 审计。记录若外发/跨机器共享，先隔离敏感信息并改回 `shareable` 范围；不得把本地受控记录当作可分享记录。

## 6. 防踩坑（实战固化）
- 脚本/命令以 `write`/`edit` 落盘再执行，避免 heredoc 转义坏（曾多次 SyntaxError/ERR_MODULE_NOT_FOUND）。
- 每个 CDP 脚本显式带 `BB_PORT=<当前 profile 端口>`，否则默认端口连不上而 ECONNREFUSED。
- 站类型判别失败、结果不明确 → 记 `outcome_unknown` 排复查，不臆断成功。
- 单跑 vs 批量：复用批量执行器，少写一次性零碎脚本。
- **标签页卫生（2026-08-27 用户要求）**：打开新一批网页标签页前，**先关闭/清理与本批无关的旧标签页**（上次批次的临时探测页、卡死页、已完成站的残留页），控制活动标签数在浏览器容量内，避免浏览器崩溃/占用过高；**人工队列接力页等必要标签例外保留**（§4）。

### 6.1 指纹浏览器服务器总客户端禁令（2026-08-27 用户硬性要求）
> **硬性禁令（任何情况）**：**禁止修改指纹浏览器服务器总客户端**（BitBrowser 管理端/主控台/总控主窗口）及其窗口/设置。即使因上下文压缩需重新识别指纹浏览器，也**只做只读检查**（profile 目录/`DevToolsActivePort`/CDP 端口），**不得创建、关闭、移动、改尺寸、改配置或写入任何管理端/总控客户端**。
- 上下文压缩后的重新识别 = 只读：读 profile / CDP 端口、attach 到**业务标签页**，不触碰服务器总控客户端。
- **仅当确有必要**（如必须核对/切换 profile 而无法绕过）时，**先询问用户并取得显式授权**，按其指示的最小操作进行；未授权一律不动。
- **唯一例外（2026-08-28 用户授权）**：**浏览器崩溃时**，允许在客户端中执行**「重新打开浏览器/重启该 profile」**这一项恢复操作，用于恢复执行环境；除此外依旧**不修改客户端任何窗口/设置/配置**。
- 违反此禁令会干扰用户对位浏览器管理端的操作并可能破坏执行环境（§17.5 固定执行环境）。

### 6.2 CDP 脚本重试审议门（2026-09-08 用户要求）
> CDP 报错、超时、空响应或“未找到元素”不等于应立即重跑。目标是用一次有证据的诊断替代无思考的脚本循环，节省时间与 token，同时不掩盖页面状态变化。

- **适用范围**：所有 CDP 的脚本/命令失败，包括连接、target 获取、DOM 查询、`Runtime.evaluate`、填表、上传、等待、导航和网络读取。最终 Submit / Publish / Gmail Send 点击**零次重试**，仍按 §7 的一次点击和三信号流程处理；短贴、长文和无法分类的内容入口按 §15 只记录、不执行，不能把通用 `Post` 当成可执行动作。
- **每次重试前必须完成三轮审议并留痕**：①证据——记录精确错误、失败命令、target ID、当前 URL/标题、页面/表单状态、最近网络或控制台信息；②假设——至少提出两个可区分的原因（如 stale target/导航、选择器或 frame 错误、页面尚未 ready、CDP 传输暂态、站点/反自动化错误），不得把“再跑一次”当作假设；③判别——先做能区分这些假设的最小**只读**检查，例如重新列 target、读取当前 DOM/iframe、确认 loading 状态或读取网络响应。
- **允许重试的唯一条件**：只读判别产生了新的、可验证的假设，且下一次操作相对上次有实质变化（新 target、重新获取元素、正确 frame、不同等待条件或已确认的单次传输恢复）。每个失败操作最多一次这样的受控重试；相同脚本、相同 target、相同参数和相同等待条件的重复执行一律禁止。
- **禁止循环**：不得用 `for`/`while`/递归 `catch` 让 CDP 命令自动重试；批量执行器必须把单次失败返回到站点决策层，而不是在工具层静默重跑。
- **停损与分流**：没有新假设、判别仍不明确、受控重试再次失败，或发现页面错误/反自动化/最终动作可能已发生时，立刻停止该站该动作。按事实记 `submission outcome unknown`、相应 blocked 状态或人工队列；不得为了“验证一下”再运行脚本。
- **记录**：每站写 `CDP retry decision`（`not applicable` / `no retry` / `retry approved` / `retry denied`）。选择 `retry approved` 或 `retry denied` 时，`CDP retry evidence` 必须包含失败摘要、两项假设、只读判别结果，以及批准重试时改变了什么；汇总中只报告经记录的重试。

## 7. 提交结果判定：杜绝「睡一下再读一次」漏判（2026-08-20 实战固化）
### 7.1 根因
- **旧法**：点击提交 → `sleep(几秒)` → 读一次页面。当站点提交后**先短暂显示成功页、随即自动跳转**（HTTP 302 / JS 跳转）回表单页或队列页时，`sleep` 后读到的已是跳转后的页 → **误判未成功**，甚至反复补投/重试。
- `waitLoad` 等 `readyState==='complete'` 也正好等到跳转结束后的页，同样漏掉成功瞬间。
- 常见误报：正文含 "submitted" 但实为 "**isn't** submitted yet"（单信号误判）。

### 7.2 修法（通用实现要求）
- **`submitAndCapture()`**：点击提交后立即以 ~150–200ms**高频采样**「当前 URL + 页面正文」，记录**第一个离开表单页的状态**——成功页在被自动跳转前即被抓到。
- **网络层兜底**：使用当前已核验的 CDP 事件订阅和 `Network` 域；必要时以 `Network.getResponseBody` 读取提交请求的**响应体**（无论之后如何跳转，回执都在）。
- **`judgeOutcome()` 严格判定**：`(URL 变化 ∨ 成功 URL) ∧ 正向文案 ∧ ¬否定词`，用否定词过滤 `isn't / not yet / not submitted / error ...`。

### 7.3 使用规则（执行前完成防重试自查）
- 判定成功 **必须先看提交后 URL**（非原表单页），**再**找明确成功文案，**再**截图证据；三信号互证才算。
- 命中「反机器人挂起（Runtime.evaluate 持续超时）/ 数学验证 / 需登录账号且无免费通道 / 需互链付费 / 类目不契合」→ **一次判定即搁置**，加入工队列记 follow-up，**不重试**。
- 真实站点实测：tipseason、tinystartups 用此正确捕获成功；zeleur/tipocode 为真·反自动化**挂起**（非漏抓），维持 `blocked — manual verification`。

### 7.4 多标签页与延迟终态核验（2026-08-21 补充；2026-08-26 触发条件收窄）
- **触发条件**：**仅当 `submitAndCapture` 首次捕获结果不明确**（无正向/负向终态、或判断冲突）时才执行本节；首次捕获即三信号互证明确的成功/失败站，直接记录并进下一站，不进入本节。
- 同一次表单提交可能保留多个同域标签页：旧的校验失败页、当前填写页和异步跳转后的感谢页可能并存。**不得只读取第一个 URL 匹配的标签页**，也不得以旧页的错误文案否定新页的结果。
- 高频采样结束后，按 `platform domain + submission-route prefix` 枚举所有匹配 CDP targets；逐个读取最终 URL、页面标题和原生正文，再以最近一次状态变化/感谢页为准。
- 对仍在 `Submitting…`、原表单页或无明确终态的项目，进行 **2–3 轮**有限的只读回执核验：每轮读取当前 target/页面，并分别按可及性查账户后台、邮箱和公开页；记录轮次、时间、URL/target 和结果。延迟检查只读，不再点击提交。
- 成功仍须满足：匹配标签页出现离开表单的 URL 或明确成功 URL，且有正向原生回执；把命中的 target ID、最终 URL 和回执摘要写入受控证据。若多个标签页结论冲突，记录为 `outcome_unknown`，优先检查邮箱或账户后台，禁止再次提交。
- **无回执交接（2026-09-17）**：完成第 2 或第 3 轮仍无明确回执时，保持当前页面和 target 不关闭，记录 `submission outcome unknown`、`Outcome-check attempts`、`Handover page` 与所有只读结果，转人工查验；这不授权重投。

### 7.5 可复用能力
- 判定：当前任务的 `submitAndCapture()` 与 `judgeOutcome()` 等价实现；若无现成实现，先在工作区建立并验证，而不是假定某个私有文件存在。
- 防重试自查：先判后动，核对 curl 可达性、框架、是否需登录与类目契合。
- 填表：对 React 受控字段使用经验证的原生输入方案（聚焦、全选、`execCommand('insertText')` 或等价方法），不再逐站盲试。

### 7.6 登录与表单校验经验（2026-08-21 补充）
- **从页面实际链接取登录路由**：不要由 `/sign-in`、`/login` 等常见命名猜测。读取“Sign in to continue”实际 `href` 后再打开；路由 404 只说明该猜测无效，不说明网站无法登录。
- **OAuth 仅在身份无歧义时自动继续**：先读取账号选择页。只有一个已授权账号、且无额外安全提示或新增权限范围时才可点击继续；多账号、恢复、密钥或异常授权提示一律保留原标签页交人工。
- **提交前读取浏览器原生字段约束**：对必填输入检查 `type`、`pattern`、`minLength`、`maxLength`、选项与 `checkValidity()`。例如 `pattern="\\d*"` 只接收数字，国际电话中的 `+`、空格或短横线会被拒绝；按元素的真实规则规范化既有资料，不能猜测。
- **优先使用站内提交状态页作为成功证据**：表单可能不显示瞬时感谢页，却跳转到“Your submissions”一类账户后台。若该页同时显示“Submission received”和当前产品的 `in review/awaiting approval`，可判定为已提交；仍需记录最终 URL、状态文本与产品标识。

### 7.7 首页优先发现当前入口（2026-08-21 用户规则）
- **每个站点先打开首页并做常规发现**：从当前导航、页脚、登录后的仪表盘、站内搜索，以及 DOM 中真实的链接、按钮、`href`、ARIA/标题属性发现现在有效的 `Submit / List / Add / Publish / Claim` 入口；用户提供的深链只作线索，不可直接视为有效投递路由。**若站点有 business/商家/企业专属区，优先从 business 通道寻找曝光入口（§18.3）**。
- **视觉识别仅为兜底（2026-09-11 用户规则）**：当且仅当常规发现未找到任何可验证的提交/曝光入口时，才使用截图或其他视觉能力，对整页**首、中、尾三段**逐段核对。若常规发现已找到可用入口，不得为了“完整性”再做首中尾视觉扫描，记录 `Visual fallback: not required — regular entry found` 及入口证据即可。
- **触发后的视觉预检完成条件**：视觉兜底一旦触发，首、中、尾均须检查并分别记录“发现入口”或“未发现入口”；页首检查导航、汉堡菜单、登录/Business 入口与悬浮按钮，页面中段检查 Hero、卡片 CTA、分类/内容区与弹层，页尾检查 footer、站点地图、账户/投稿/合作/联系我们等入口。对懒加载、无限滚动或页脚折叠页面，应滚动/展开至实际页尾。仅在常规发现和已触发的视觉兜底均未发现可用入口时，才可作出首页无入口、付费路径唯一或不适格的结论。把视觉候选、所在区段和截图/滚动位置记入受控证据。
- **视觉发现后必须验证**：对视觉候选项，读取其真实可操作控件、`href` 或点击后的最终 URL 和重定向链；无法取得真实入口、只是一张图片、泛化分类词（如普通 `Business` 分类）或历史内容时，不得推断为提交/商家通道。视觉检查用于补漏与定位，不替代首页实际路由、字段、免费性、身份与条款预检。
- 将“首页发现的当前入口”与原始深链逐一比对：若深链重定向、404、显示旧产品名或进入失效流程，以首页当前入口为准，并把路线变化与最终路径记入受控证据和记录。
- 仅当首页及其明确链接均没有可用入口，才标记 `unavailable`；不得因为旧深链失效就跳过首页发现。
- 不得把首页上的推广、付费升级、外部广告或非目录内容误当投递入口；进入表单前仍须完成资格、免费/付费、验证和幂等检查。

### 7.8 不得停在付费/合作路径，必须完成「首页可见入口 + 站点重定向」核验（用户要求，2026-08-27）
> 实测漏投根因：过早停在 Partner / Sponsored / Paid 提交等**付费或合作路径**，未完成首页可见常规入口的查找与重定向核验。**避免此问题**：
- **遇到付费/合作路径只在原处标记"付费跳过/不执行"，继续在首页找常规自由入口**：Partner、Sponsored、Paid listing、广告位、Premium submit 等出现时，**不得以此作为站点唯一结论**；继续按 §19.1 七类曝光入口核查是否存在免费/常规入口（含 business 通道 §18.3）。
- **完成"首页可见入口"核验**：首页导航、页脚、登录后仪表盘、站内搜索逐处查找当前有效的 `Submit/List/Add/Publish/Claim/资料创建` 入口；发现即采用（含登录后可见的入口，按 §18.2 先登录再看）。
- **完成"站点重定向"核验**：对原始深链与每个候选入口**跟随重定向（301/302/JS 跳转）走到底**，记录最终 URL（表单页/登录页/跳往付费或失效页）；深链若被重定向到付费/合作页，只说明该深链是推广路径，仍需回首页找常规入口；常规入口若重定向到登录/注册/验证，按 §18 处理后继续。
- **记录**：每站写入「付费路径（仅跳过）+ 首页可见常规入口（最终 URL）+ 重定向链」；两项核验都完成后仍无免费/常规入口，才判 `unavailable`。

### 7.9 React 受控表单稳健填写 + 「首个错误即停」+ 后台回查（2026-08-27 实战教训）
> 实测失误：CDP 填入被页面重置（名称/描述未稳定写入）、未在首个 "Something went wrong" 停止、后台无草稿仍继续。**避免复发**：
- **受控表单必须回读确认**：填入后用 CDP **读取字段实际 value**；若被页面重置（受控组件重新渲染清空），改用更可靠法（聚焦+全选+`execCommand('insertText')` 或真实键入），并在**提交前最终校验**必填字段 DOM value＝目标值且非空；未确认稳定写入前**不得点提交**。
- **首个明确错误即停（fail-fast）**：遇站内明确错误回执（"Something went wrong"、页面报错、校验拒绝）→ **立即停止该站**，记 `outcome_unknown`/`blocked — manual verification`（附错误回执与后台状态证据）→ 不重试、不进入后续步骤（§8 纪律）。
- **后台回查为准**：提交后回查账户后台/记录区，**出现产品草稿或待审记录才算成功路径**；后台无记录 → 如实记为未成功，不臆断。
- **标签页占用纪律**：邮箱/验证等操作**不占用必要标签**（如 Gmail 收件页）；被占用的必要标签**立即恢复**；开批前清理无关标签（§6 标签页卫生）。
- 登录成功但第 1 步报错且后台无草稿的站 → 记 `outcome_unknown` 待人工复查，不重复提交。

## 8. 批处理操作纪律（用户明确要求，2026-08-20）
> 服务的最终口径：**宁可少做、不臆断、不重复，把不确定/阻塞项完整交给人工收尾**。
- **减少无意义且低效的试错和重试**：判定不明确的、阻塞的、反自动化的，**不再反复尝试**。
- **直接搁置、转向其它网站**：每站以「先判后动 + 提交即捕获 + 三信号判定」处理一次；命中阻塞分支（反机器人/需账号无免费通道/互链付费/类目不契合/网络不可达）→ 立即记录并搁置，继续处理清单内下一站，**不要在同一站上耗轮次**。
- **全部网站跑完之后统一说明情况，由人工收尾**：不逐站打断汇报；批内所有站处理完毕后再给出完整情况说明（每站状态 + 阻塞原因 + 人工需做什么），交由人工收尾。
- **批内连续执行、不做阶段性汇报（2026-08-27 再次强调）**：本批开始后**不再做阶段/中途汇报**（进度、单站结果、猜测性同步均不发）；**连续跑完**全部站点（每站一次判定、阻塞即跳过保留标签页），完成记录审计后**统一一次性交付**（§20 逐站明细）。仅两类情况允许期间与用户交互：**需用户授权/抉择的硬关口**（支付、强制互链、账号归属异常、总控客户端必要操作等）与**用户主动发问**。
- **凭证统一口径**：站点已注册账号需改密/找回密码时，只使用受控凭证库中的凭证别名；不在技能、日志或共享记录中写入口令。
- **归属/配置项新要求**：涉及浏览器 profile、后端、账号等新约束时，遵循用户当前指定（例如 user-required BitBrowser profile / kernel）；记录只在可验证证据下更新。

### 8.1 人机协同默认分工（用户明确要求，2026-08-24）
- **机器先做完整预处理**：从首页发现当前入口，生成字段卡，填入已核实事实、上传图片、保存草稿，并在最终动作前完成免费/条款/验证/幂等检查。
- **人工只处理不可自动化的关口**：CAPTCHA、账号选择与身份声明、需要个人判断的异常、失效控件，以及需单独授权的付款、官网改动、徽章和互链。
- **集中而非逐站打断**：机器保留原标签页并批量列出人工队列；用户完成短时效验证后，机器立即核验同一标签页并优先处理即将过期的令牌。
- **人工动作后的收尾必须自动化**：机器读取后台、邮箱或公开页回执，写入可审计状态；没有明确回执的一律标为 `submission outcome unknown`，不因人工点击而重复提交。

## 9. 批次轮次策略：成功率即效率（用户明确要求，2026-08-20）
> 衡量本轮运行时效率的核心指标是**成功率**（而非批量投递的数量/吞吐）。
- **成功率即效率**：宁可放慢、逐站做透，也不要"多而不成"；以可核验的成功提交为产出。
- **首轮（第 1 轮）**：对清单中**没有阻碍、可直接成功批量提交**的网站做**批量提交**（一次性批量处理所有无阻碍站）。
- **后续轮（第 2 轮起）**：提交**一律一个一个网站进行**（单站串行、逐站聚焦）——复查、复核、阻塞站重试、人工完成后补投等，都按单站独立推进，避免在多站间分散试错、互相干扰；每站完成后核验再进下一站。
- 阻塞/不确定站仍按 §8：立即搁置、全部跑完统一说明、交人工收尾。

## 10. 调用/启动顺序：四阶段确认（用户明确要求，2026-08-20）
> 调用 SPD-V1 独立版开始工作前，必须按以下顺序完成，**不可跳步**。
- **阶段一 · 先确认内部资料**：核对/提取本次要投的产品的**内部资料**——已核实的 product profile（品牌/官方拼写/官网/公司/联系方式/宣传文案/配图资产）、brand rules、凭证别名与受控凭证库、所需图片（已合规）。
- **阶段二 · 再确认技术路径和可用工具**：确认**技术路径**（浏览器 profile / CDP 端口 / 后端 / 是否需要 computer-use / 自动化边界）与**可用工具**（当前已核验的 CDP/CU 接口、批量调度、记录生成、`audit_submission_record.py` 和防重试自查），确认环境就绪、`BB_PORT` 正确。**必须询问用户：自动化执行方式用 CDP（DevTools 直连，推荐）还是 CU（Computer Use 桌面操控）**——以用户选择为准，未确认前不开始。
- **阶段三 · 之后确认系统环境所需权限与授权**：确认**当前电脑系统环境对应的所需权限**（例如：控制浏览器、截屏/辅助功能、读写工作目录等是否可用），以及**所需授权**（例如：调用飞书 lark CLI 读邮箱完成验证、使用受控凭证库/统一口令等是否已授权）。权限/授权缺失的项先补齐或交人工，不带着缺权限强行开跑。
- **阶段四 · 最后提供网站列表开始工作**：在资料、技术能力、权限与授权都确认之后，才给出/收拢**网站列表**，并按 §8/§9/§11 纪律开始执行（先判后动、按 §11 准入、首轮批量无阻碍站、后续单站逐个、阻塞搁置、跑完统一人工收尾）。
- 意义：**先有准确资料、可跑的技术底座、足够的权限与授权，才谈得上投递**；避免"资料未核 / 环境未就绪 / 权限缺失"下强行开跑导致的返工与试错。

## 11. 可投递对象准入标准（用户明确要求，2026-08-20）
> 「成功率即效率」前提下，入队标准以**能否可投**为准，而非以目录所属垂直/本地向/内容形态一刀切。
- **判定口径**：只要该站**能提交站点 URL** 且**能选到相关分类** → 一律**纳入可投递对象**，进入投递队列。
- **不再仅因"目录是别的垂直/本地向/内容站"就判 `ineligible`**：唯一的关键看它是否**具备「提交 URL + 可选相关分类」的能力**。
- **仍搁置/不投的情形**：确实**无法提交 URL**（无收录入口）、或**选不到任何相关分类**、或命中 §8 硬障碍（反自动化挂起/需账号无免费通道/互链付费/网络不可达）。
- 执行：按 §10 四阶段确认后，按此标准把"具备 URL 提交 + 可分类"的站纳入队列，并按 §9（首轮批量无阻碍站；第 2 轮起单站逐个）处理。

### 11.1 投递前站内去重核验（2026-08-27 用户要求；站内可搜到即不投）
> 实测问题：**大量出现"站内已能搜到该产品，却仍然执行投递"**（重复投递、浪费轮次）。**避免复发**：投递前必须做站内去重核验，命中即不投、只记录。
- **执行前置检查（预检阶段，按序）**：
  1. **站内搜索**：先用站点真实的搜索控件输入并触发**官方品牌/产品拼写**，再按固定查询集检索其标题词序/拼写变体、规范 URL（含与不含尾部 `/`）和裸域名。每一次查询都必须记录输入词、触发动作、结果页 URL、结果数、可见候选标题和截图/页面证据；未真正触发、读取到旧页面、或未等异步结果渲染，均不构成“无结果”。每个候选均须核验其实际出站 URL 的归一化结果。若解析到规范主机或规范 URL，立即判 `duplicate — no action`；
  2. **账户后台记录区**：登录后检查 My Listings / Submissions / 草稿 / 待审，已有该产品记录 → 不重投；
  3. **近期列表/分类列表**：Recent / New listings 或相关分类页翻找本站品牌 → 命中即不投。
- **命中处理**：记录「查询词、触发动作、结果数、候选标题、候选归一化出站 URL、结果页 URL/截图 + 判定 duplicate — no action」；**不执行投递**，继续下一站（§9）。用户明确确认已收录时，直接以该确认作为本批次的去重证据，不自动复核或重投。
- **去重=前置硬门槛，不可降级（2026-08-27 用户复盘）**：
  - **先完成站内四类查询并逐条打开核验，再进入填表**：① 站内搜索（品牌名/官网 URL）② 账户后台记录区 ③ 近期/分类列表 ④ 站内直达/首页可及列表；命中项**逐条打开**核对（不能只看标题列表就下结论）——**任何"直接填表"指令都不豁免此步**；
  - **首页超时 ≠ 无法预检**：首页加载超时/失败不清零预检与去重责任，改用可及路径（直达 URL/缓存/搜索/后台）继续完成四类查询，不得因此跳过；
  - **提交时的 "URL already exists" 只作失败兜底提示，不作去重依据**——去重必须在**提交前**完成并留痕，前置为硬门槛，避免浪费一次提交；
  - **直链/重试时重新跑完整去重**：改走深链、重开页面或重试同一站时，**不得沿用旧的"预检通过"结论**，须重跑完整四类查询。
  - **未证明完成≠未收录；改走一次直接尝试（2026-09-04 用户规则）**：未留存品牌词查询的输入、触发和已读取结果证据，或任一必要搜索/候选核验因控件、异步加载、分页、跳转或访问限制而未证明完成时，不得把模型“没看到结果”写成 `cleared`，也不得仅因去重未完成中断搁置。记录 `Duplicate check: inconclusive — user-authorized direct attempt`、具体缺口、已完成检查和批次授权引用；在其它资格、免费性、条款和验证门槛均通过后，继续完成表单并作**一次**最终提交。将原生“URL already exists”或等价重复回执记录为 `duplicate — no action`；没有明确重复或成功回执时，按 §7 记 `submission outcome unknown` 并禁止重试。
- 品牌词优先的固定查询集与其他三类查询均已留证且未命中时，记 `Duplicate check: cleared`；否则按上述受控直接尝试路径进入真实投递（按 §16/§16.1 填全，§7.9 提交回查）。
- **匹配口径：词序无关 / 模糊匹配（2026-08-27 用户要求）**——**标题词序不同不得作为"未收录"依据**：
  - **URL 优先**：条目中出现本站**规范官网 URL（主域或路径）→ 直接判已收录**，无论标题怎么写；
  - **品牌模糊匹配**：标题做**归一化**（小写、去标点、去空格/连字符变体）后，按**显著词重叠**匹配（品牌词如 heydream、ai；含品牌名或品牌名+产品词组合即命中），**不要求全串精确、不要求词序一致**；
  - 品牌变体（HeyDream AI / Hey Dream AI / Heydream 等）视同命中；仅当**标题与品牌完全无关、且无官网 URL**才认为未见收录；

## 17. 人机协同效率协议（用户明确要求，2026-08-24）

> 目标：把人工时间只用在必须由人承担的短时、高风险动作；由 agent 连续处理可复用、可审计的页面工作。

1. **Agent 先完成可逆工作**：对非内容编辑器入口，从首页发现当前入口、选择真实相关分类、填入已批准字段卡、上传合规图片、按 §18.4 选择无费用营销订阅并关闭付费升级，并在每次状态变化后记录证据。
2. **人工只完成保留动作**：**强反自动化（reCAPTCHA/Turnstile/Cloudflare/复杂图片选择）、支付**，以及未授权/异常的最终 Submit；短贴/长文内容入口直接记为不执行，不交人工完成或发布。**条款勾选、登录、注册、验证、邮箱验证已在批次一次性授权范围内（§18）；低风险验证先由 agent 自动尝试（§18.1 分级），失败/强反才归人工**。不得外包/注入强反自动化校验，也不代付。
3. **先预填，后验证并提交（2026-09-17）**：非内容编辑器的正常场景按 §18 由 agent 自动完成验证与提交；一旦出现无法自动完成的验证，先预填全部可如实填写字段、上传适用素材并选择无费用营销订阅，再保留原标签页。由用户完成验证；若验证码必须和提交连续完成，用户立即自行最终提交，否则由用户交回后再继续获授权的下一步。§15 内容编辑器不适用本条。
4. **阻塞即入队，不在单站试错**：遇验证、条款、登录异常、支付、互链或不明确页面状态，保留原标签页并记录所需人工动作，立刻继续其它站点；批末集中人工收尾。

7. **把字段卡作为交接面**：为每站准备标题、长短描述、分类、联系别名、素材、营销订阅状态和明确留空项。人工接手时只需核验剩余字段并连续完成验证/最终提交。

- 每个目标根域名、每个官方联系路由、每个产品在同一授权批次最多一封首封邮件。禁止 CC、BCC、邮件列表、群发、自动催稿、自动回复、换地址重发或再次点击 Send。
- 共享记录只保留收件人别名、官方 Contact 来源和受控证据；不得写入明文收件人邮箱、完整 Gmail 链接、邮件线程 ID 或私密会话信息。

### 18.1 验证分级与自动尝试（用户明确要求，2026-08-26）
> **原则：遇验证先自动尝试完成低风险验证，再谈搁置**——不接受"一见验证码就一律人工"；分级自动尝试，失败/超限才转人工。任何自动尝试都为**站点原生交互**，不外包第三方解算、不注入 token、不解绕强校验。
- **一级 · 低风险原生验证（自动 ≤2 次）**：表单内嵌算术/逻辑题字段、邮箱验证码/验证链接（在已授权邮箱内读取并完成）、站点自身的普通校验步骤——agent **先自动尝试**，≤2 次成功即继续；2 次仍失败 → 停止转人工。
- **二级 · 普通交互式验证（自动 ≤1 次）**：站点提供的常规人机步骤（如原生 click 型、简单滑块/点选类）——agent 按站点原生交互**自动尝试 1 次**；失败即转人工（保留标签页、记录）。
- **三级 · 强反自动化（0 次自动尝试）**：reCAPTCHA v2/v3、Turnstile、Cloudflare challenge、复杂图片选择等强反机器人挑战——**不做解绕/不外包/不注入**，直接人工队列（合规红线，不可松）。
- 每次自动尝试如实记录（站点/验证类型/尝试数/结果）；按级失败后转人工队列，不反复重试。

### 18.2 登录/注册/验证优先级阶梯（用户明确要求，2026-08-26）
> **一律先登录**：对每站先走登录流程，未登录不进表单；按下列顺序逐级下探，命中可用的即用，失败/不存在再降级下一级。
1. **谷歌直接登录（首选）**：用浏览器 profile 已登录的 Google 账号（alias-google-1）走站点 Google OAuth 直接登录；登录成功即继续投递。
2. **谷歌账号（次选）**：无 Google OAuth 或失败时，改用 Google 账号名下的流程——**登录** → 账号不存在则**注册** → 登录被拒则**找回密码**（统一口令，见受控凭证库）。
3. **企业邮箱（三选，兜底）**：Google 路径不可用时，用企业邮箱（alias-corp-1）走**登录 → 注册 → 找回密码**。
4. **邮箱验证授权口径**：
   - **Google 邮箱验证（alias-google-1）＝全授权**：agent 自动读取并完成验证（§18）。
   - **企业邮箱验证（alias-corp-1）＝搁置**：不合自动验证，**统一最后交人工批量处理**（保留标签页、记入批末人工队列）。
5. 约束：仍不解绕第三方 CAPTCHA（§18.1）；注册/登录/找回密码/条款勾选均在 §18 一次性授权范围内；动作失败按 §18.1 上限处理。

### 18.3 优先走 business 通道，寻找曝光入口（用户明确要求，2026-08-26）
- **优先 business 通道**：凡站点区分个人与商业（business / supplier / merchant / provider / company / 商家·企业），**优先注册/登录 business 通道**（以品牌/公司实体身份），并**从中寻找曝光入口**：品牌展示页/公司主页、claim、目录 / listing 入口、business profile 中的官网链接位等。
- 仅当该站**无 business 通道**或 business 通道不通时，才退回 §18.2 一般登录/注册路径。
- 配合：档案类按 **§16.1 填全**；曝光入口归入 **§19** 操作对象；建号/验证仍走 §18 / §18.1 / §18.2。

## 19. 工作对象扩展：品牌 URL 可展示即可操作（用户明确要求，2026-08-26）
> 投递/操作对象**不限于目录“URL 提交表单”**——**凡符合本节可执行类型、能让品牌或 URL 得到展示的入口都可操作**，追求全面覆盖；后期按实际数据复查筛选。
- **操作类型（均属可执行对象）**：目录/收录 **URL 提交**；**品牌账户资料建立（account / profile 创建并填写品牌资料，§16.1 档案填全，§18.2 登录阶梯）**；**公司/企业档案创建**（company / business / provider profile）；**项目/需求发布**；**免费广告（免费广告/分类广告/免费发布）**；**新闻稿（免费新闻稿/公告发布）**；**官方 Contact 邮件外链申请**（§19.2）；工具/应用收录、链接展示页、账号主页、清单条目及其他**公开可见展示品牌 URL** 的非内容编辑器入口。
- **识别但不执行**：公开短贴 Note / status / 动态，以及所有长文 Post / Article / Blog / Story / Guest article 和无法可靠分类的内容编辑器，均按 §15 记录；不得输入、预填、保存草稿、交人工、提交或发布。
- **仍守合规**：内容**真实、一次性、原生**——不虚构服务资质、公司实体、项目需求与预算、客户评价；**免费广告/新闻稿须用真实可证实的公司或产品事实（不虚构发布公告、数据、成果或合作）**、使用免费档、链接官方 URL；不付费、不解绕第三方 CAPTCHA（§18.1）、锚文本用官方品牌/裸 URL、如实记录（§0/§15 口径，本节约等于 §15 的统合范围）。
- **执行**：登录/注册/验证按 §18.2 阶梯；首页发现当前入口 → 预检（公开可见、含品牌 URL 展示位、免费性、条款、身份归属）→ 按 §9 轮次操作；阻塞即跳过、批末统一人工收尾；提交或发布后不重复执行。

### 19.1 每站曝光需求识别：必做、写入记录、可审计（用户明确要求，2026-08-27）
> 实测教训：**不能只识别"URL 提交表单"就算完成任务**。目标口径＝**品牌曝光（品牌/URL 可展示）**；URL 提交只是其中一类。每站在首页发现入口时必须**显式执行本节识别**，并把结果写进该站记录（不写视为未识别）。
- **逐项检查（按序，首项命中即优先执行，仍继续查后续项以记录全量曝光入口）**：
  1. business / 商家 / 企业专属区 → **优先 business 通道**找曝光入口（§18.3）；
  2. Company / Business / Provider **档案创建**入口（含 Claim）；
  3. 目录 / listing / Add / Submit/**URL 提交**入口；
  4. **内容编辑器**：短贴 Note / status / 动态及长文 Post / Article / Blog / Story 等；只按 §15 分类并记录，绝不执行；
  5. **免费广告 / 分类广告 / 免费发布**入口；
  6. **新闻稿 / 公告发布**入口；
  7. **账号主页 / 资料页链接位**（建号后填品牌 URL）；
  8. **project / showcase / maker / 作品集 类提交入口**（"Submit your project / Add project / Showcase / Ship it" 等）——**把品牌网站首页作为 project 页上传/登记**，实质同样是品牌首页 URL 曝光入口，**必须识别并执行**，不得当非投递对象跳过。
  9. **官方 Contact / 投稿 / 资源推荐 / 合作邮件入口**：仅目标站官方页面公开的联系邮箱或 `mailto:`；按 §19.2 预检，不能从第三方资料抓取邮箱。
- **“Submit Listing for Review / Review Submission / Submit for Approval”等审核型提交入口同样属于投递对象**：按其实际表单/审核流程检查免费性、付款、互链和验证；不能因按钮文案是“审核”而忽略。若当前入口仅通向付费方案，记录“已识别的审核型 listing 入口 + paid-only”，不得付款或虚报已提交。
- **记录要求**：每站记录「识别到的曝光入口清单（类型 + 入口 URL）+ 选择的执行类型」，与投递状态一并写入记录（§20 逐站交付时引用）。
- **若无可执行类且只发现内容编辑器**，记录 `short note — no action`、`long post — no action` 或 `unknown — no action`，状态记 `ineligible`；不得转人工或把它当可执行曝光入口。只有没有任何曝光入口时才 `unavailable`。有可执行类即执行该类（优先级：business 通道曝光 > 档案/listing > project > 免费广告/新闻稿 > 官方 Contact 邮件 > URL 提交）。

### 19.2 官方 Contact 邮件外链申请：发现、撰写、发送与回执

> 邮件是独立投递类型，不是目录表单，也不是站内短贴/长文发布。其最终结果只能说明“Gmail 已发送”或“发送结果不明”；没有公开链接核验，绝不写成已收录、已获外链或已发布。

1. **发现与收件人**：只接受目标站首页、页脚或其明确链接页面公开的 Contact、投稿、资源推荐、工具收录或合作入口中的邮箱/`mailto:`。检查该入口是否适合接收此类建议；不得爬取第三方、个人、`no-reply`、隐私、法务或明显不处理投稿的邮箱。将实际收件人保存为受控证据，在记录中只写收件人别名和官方来源证据。
2. **发送前去重**：除 §22 的站内品牌去重外，在 Gmail 的 Sent、Drafts、All Mail 和当前记录中检索该品牌、规范 URL、目标域名和联系路由。发现既有同品牌/同官网的邮件、草稿或会话，记 `duplicate — no action`，不发送。检索不完整时，只有当前批次邮件授权同时明确允许直接尝试，才可记 `inconclusive — user-authorized direct attempt` 并发送一次。
3. **撰写**：用目标站页面语言；无法判断时用简洁英文。逐站改写，说明真实产品、规范 URL 和与该站资源/目录的具体相关性，请对方自行决定是否纳入。不得伪造身份、关系、用户、数据、奖项或合作；不得索要 dofollow、保证排名、互链或付费安排；不得请求对方撰写或发布短贴、长文、客座文章。
4. **最终动作**：发送前核验 Gmail `From` 为已授权别名、`To` 为受控收件人别名、CC/BCC 为空、正文和链接回读一致。点击 `Send` 一次；任何脚本、控件或网络异常都不得导致第二次发送。记录 Gmail 原生“已发送”提示和/或匹配的 Sent 副本为受控证据。
5. **结果**：有明确 Gmail 发送回执时记 `email sent — awaiting reply`；这不表示送达、阅读、收录、外链或发布。没有明确回执时，连续做 2–3 轮只读检查（当前撰写/线程、Sent/All Mail、Drafts/Outbox），保留 Gmail 页面，记 `email send outcome unknown`，绝不重发。不得自动回复或自动催稿。

## 20. 汇总交付：逐站说明，不以总数代替明细（用户明确要求，2026-08-27）

- 每次向用户交付投递汇总时，必须逐一列出本批次每个网站，而不是只给状态计数。
- 每站至少包含：网站名称/域名、最终状态、已做动作或保留的页面状态、可用的原生证据、以及未继续或不重投的具体理由。
- 对用户明确标记为已提交的网站，写明“用户标记”，保留其回执原文摘要；除非用户另行要求，不做自动复核或重投。
- 对验证码、强制互链、付费、条款/权限异常、重复、站点不可用及结果不明，分别说明对应阻塞或去重依据；不得以笼统的“已跳过”替代。
- 对官方 Contact 邮件，逐站写明“邮件已发送，等待回复”或“发送结果不明”，并明确它不等于已收录、已获外链或已发布；不得把它并入目录已提交或公开链接数量。
- **汇总必须附记录**：每次汇总后附上本批次对应的本地投递记录链接；若涉及多个记录，逐一列出。若某站或整批尚未建立记录，必须明确标为“记录缺失”，不得暗示已留档。
- 可在逐站明细后追加总数和下一步人工队列，但总数不能取代逐站明细。

## 21. 互链字段与验证码批量交接（用户明确要求，2026-08-27）

- **互链不是默认阻塞条件**：先读取字段的原生 `required` 状态、校验规则和页面明示条款。仅当互链 URL、代码或站点改动被明确标为必填/不提供则不能提交时，才按强制互链处理。
- 若互链字段是可选项，则必须留空；不得填入虚构 URL、代码或承诺，也不得因页面出现互链字段而放弃投递。继续填写所有真实产品字段并走正常提交流程。
- 遇第三方 CAPTCHA / Turnstile / Cloudflare 等验证码时，不绕过、不反复尝试。对非内容编辑器的可执行表单，Agent 必须先将所有可如实填写的普通字段（含描述和合规图片）完整预填，将可选互链字段留空，关闭付费升级，并按 §18.4 选择无费用营销订阅；随后保留原标签页，不得留下空表或关闭交接页。§15 内容编辑器不适用本条。
- 同批次所有验证码阻塞站点应连续处理后集中交接：最终在各自已预填页面等待用户依次人工验证并立即提交。记录每个标签页的站点、URL、剩余动作和字段状态；不得在验证码前后重复开表或重投。

## 22. 目录预检先站内去重（用户明确要求，2026-08-27）

- 对目录/收录站点，进入提交表单前必须优先使用其首页或站内可用的搜索入口，以品牌名和规范 URL 检索现有条目；**若首页没有搜索控件，或目录搜索仅在 `Submit / Add Site / Submit Link` 当前表单页提供，必须在该表单页完成同样的站内搜索后再填写。** 将结果写入预检证据。
- **检索必须多维而非只比标题**：依次检索规范 URL（含/不含尾部 `/`）、裸域名、官方品牌/产品拼写，以及从官网标题、搜索候选或既有条目发现的词序/标题变体（例如 `AI Music Maker` 与 `Music Maker AI`）。逐条打开或读取候选结果的实际出站 URL，按 hostname 与规范 URL 归一化比对；标题不同、描述旧或词序变化，均不得作为未收录的理由。
- **记录必须可复核**：受控证据至少保留每个查询词、结果数量、候选标题和候选的归一化出站 URL；任一候选指向规范站点即立即标记 `duplicate — no action`，撤出预填/验证码/人工队列，不得继续最终提交。
- 若站内搜索显示已有收录、已有待审条目，或用户明确确认该站“曾提交且已收录”，直接标记为 `duplicate — no action`，不得继续填写、验证或重投。
- 用户明确确认已收录时，以该确认作为当前批次的去重依据；不额外耗时做公开页、邮箱或后台复核，除非用户另行要求。

## 23. 去重未完成时的直接尝试（用户明确要求，2026-09-04）

- 若已完成首页、账户区、提交页及可及列表的检查，但站点**没有原生搜索入口、候选列表或可用后台记录区**，记录 `Duplicate check: not available — user-authorized direct attempt`；若搜索控件、异步结果、分页、跳转或候选外链核验使去重无法完成，记录 `Duplicate check: inconclusive — user-authorized direct attempt`。两者都不得误写成“已去重通过”，并须写明已检查界面、缺失/失败能力和批次授权引用。
- 在当前批次获得用户明确“去重未完成时直接尝试提交”授权后，可继续完成真实、免费、非强制互链、无强反自动化阻塞的表单与一次最终提交；这是一项**去重例外**，不放宽本地幂等记录、付费、强制互链、真实性、验证码或一击后不重试规则。
- 若表单/账户随后提供 URL 已存在或候选条目，立即停止并记录 `duplicate — no action`；不得以该异常作为重复提交的理由。
- 审计记录须附用户授权引用与“去重未完成”的具体证据；最终汇总把该站标注为“按用户授权直接尝试（去重未完成）”。
